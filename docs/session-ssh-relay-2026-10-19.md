# SSH 中转配置会话记录

日期：2026-10-19

本记录只保留方案、决策和验证结果。真实公网地址、内网地址、端口和账号名均使用占位符表示。

## 目标

让位于受限内网中的目标设备通过云服务器向外建立 SSH 反向隧道，使外部使用者可以通过云服务器安全跳转登录目标设备，同时不获得云服务器管理权限，也不把整个内网暴露到公网。

## 最终架构

```text
目标设备 -- RELAY_USER / -R --> 云服务器 CLOUD_PUBLIC_HOST
                                      |
                                      | 127.0.0.1:TUNNEL_PORT
                                      v
                                目标设备 SSH:TARGET_SSH_PORT

外部电脑 -- JUMP_USER / ProxyJump --> 云服务器
管理员   -- ADMIN_USER -----------> 云服务器管理 shell
```

账号职责：

- `RELAY_USER`：目标设备使用，只允许远程（`-R`）转发。
- `JUMP_USER`：外部使用者使用，只允许 `ProxyJump` 到 `127.0.0.1:TUNNEL_PORT`。
- `ADMIN_USER`：管理员使用，不对外共享。

## 关键决策

1. 使用云服务器作为中转，不在内网路由器上直接映射目标设备 SSH 端口。
2. 反向隧道端口只绑定云服务器回环地址 `127.0.0.1`，不监听公网地址。
3. `RELAY_USER` 和 `JUMP_USER` 分开，分别限制为远程转发和本地转发。
4. 每位外部使用者使用两把独立密钥：一把登录跳板账号，一把登录目标设备账号。
5. 外部使用者不共享管理员账号；目标设备长期应为每人配置独立系统账号。
6. 所有教程中的可执行命令使用单行格式，避免反斜杠续行造成复制执行错误。
7. 对外发布的教程使用参数化占位符，不保存真实地址、端口或账号信息。

## 已确认的故障原因

### 直接访问内网设备失败

当前执行环境无法直接访问内网地址；用户自己的电脑可以访问，说明用户电脑具备目标网络或 VPN 路由。云服务器反向隧道解决了这个网络方向问题。

### `usermod: no changes`

表示目标系统账号已经存在且请求的属性没有变化。它不能证明账号曾用于 SSH 中转，需要结合账号目录、`authorized_keys`、SSH 配置和日志判断。

### Wukong relay 日志

应用日志中的 `wukong-auth-relay` 属于应用层 Python 中转进程，进程用户和监听端口需要单独核实。它与 SSH 的 `RELAY_USER` 账号不是同一概念。

### 多行命令失败

复制两个反斜杠时，shell 会把反斜杠当作参数，导致用户名格式错误、下一行变成 `command not found`，后续命令再出现 `invalid user`。因此教程统一使用单行可执行命令。

### `sudoedit` 拒绝编辑

当当前用户本身拥有目标目录时，`sudoedit` 会拒绝在可写目录中提升权限编辑，以防止符号链接替换攻击。此时应由文件所有者直接编辑，或由管理员以目标用户身份编辑。

## 后续维护原则

- 更换云服务器、目标设备或端口时，只修改参数表和对应配置项。
- 新增外部使用者时，只添加其公钥，不共享私钥和管理员账号。
- 撤销访问时，同时从跳板账号和目标设备账号删除对应公钥。
- 修改 SSH 服务配置前先运行配置检查，并保留当前管理会话。
- 不开放中转端口的公网监听，不使用 `0.0.0.0` 作为远程转发绑定地址。
- 目标设备公钥登录验证成功后，再考虑关闭密码登录。
